# Framefolio 重构方案：Web 管理端 + R2 对象存储双源

本文档针对「NAS / Docker 部署下照片管理不便」与「缺少 CDN 导致访问慢」两个痛点，给出重构方案、破坏性评估与性能分析。

前置文档：[`DEV.md`](./DEV.md)（产品需求）、[`IMPLEMENTATION_PLAN.md`](./IMPLEMENTATION_PLAN.md)（MVP 计划）。

---

## 0. 结论摘要

| 问题           | 结论                                                                                                  |
| -------------- | ----------------------------------------------------------------------------------------------------- |
| 是否要重写？   | **不需要。** 同步管线、指纹命名、布局算法、Viewer 全部保留。                                          |
| 破坏性大吗？   | **分层可控。** Web 管理端本身几乎零破坏（纯新增）；改动集中在运行时边界与索引结构。                   |
| 有性能问题吗？ | **不会卡。** 已实测：同步期间网页响应无劣化，只占 1 个 CPU 核心。瓶颈是首次全量导入的时间与内存峰值。 |
| 最该先做什么？ | **Web 管理端 + 「立即同步」按钮。** 直接消除「进终端敲命令」的痛点，投入最小。                        |

核心判断：**你的主痛点是"每次更新照片都要执行 CLI 命令"。** 照片经 SMB 拷入 bind mount 的 `data/originals/` 本身是顺畅的，唯一卡点就是那条命令。因此把这条命令变成一个**网页按钮**，就能以最低成本解决绝大部分问题；Web 上传的价值主要在**手机端直传**与**无 SMB 的场景**，是补充而非主体。

> **同步的触发入口只有两个，全部是显式动作：管理端「立即同步」按钮 / 命令行 CLI。**
> **不做定时轮询，也不做「上传/删除后自动触发」。** 详见 §5、§6.4。

## 0.5 重构完成后的使用方式（终点定义）

> 本节是**以结果为导向的锚点**：先锁定"做完之后怎么用"，再倒推开发范围，避免开发过程中偏离。
> 若本节描述与你预期不符，请先纠正本节，再开始开发。

### A. 首次部署（从当前版本升级）

**升级就是普通的 `pull` + `up -d`，没有额外步骤，也不需要先跑 CLI。**

```bash
# 1. 拿到新版（见 §0.6 决策 C1：镜像来源）
docker compose -f compose.image.yml pull

# 2. 释放旧容器（新版空着就行，稍后统一 up）
docker compose -f compose.image.yml down

# 3. 写配置（在 compose.image.yml 同目录）
cat > .env <<'EOF'
FRAMEFOLIO_PORT=3123
PUID=1000
PGID=1000

# 管理端口令（不设置则管理端整体不可用）
FRAMEFOLIO_ADMIN_PASSWORD=换成你自己的强口令
EOF

# 4. 启动
docker compose -f compose.image.yml up -d gallery
```

然后打开 `https://你的域名/admin`，点一次「**立即同步**」:

- **管理端在同步前也能正常使用**：照片列表会显示全部照片为「待新增」，并给出「索引需要重建」的提示
- 点完同步，公开画廊即恢复正常

> **为什么可以直接启动**：新版本的索引格式与旧版不同，旧索引会被判为无效，因此**公开画廊（`/api/photos`）在你首次同步前会显示"加载失败"**。
>
> 管理端同样要读索引，但它**刻意采用了容错读取**：读不出旧索引时按「空索引」处理，页面照常渲染，并提示索引需要重建。这样管理端在升级后始终可用——否则就会出现"必须用管理端修索引，但管理端因为索引坏了而打不开"的死锁。
>
> 公开画廊则相反，**保持严格**：宁可明确报错，也不能静默返回空列表，否则看起来像"照片全被删了"。
>
> ⚠️ 唯一的代价：**首次同步会重新生成全部缩略图**（因为新版拿不到旧格式的缓存，只能从原图重建）。这是一次性的，之后的同步全是增量。照片数量多时需等待几分钟。
>
> **不需要**：备份旧索引、手动删 `data/generated/`、或先跑 CLI 全量同步。这些都不会让上面的过程更快或更安全。

**关于兼容性（已确认）**：本项目目前只有你一个使用者，**明确允许破坏性更新**，因此新版本**不写旧索引兼容代码**。重构就当新项目做，旧版的**展示逻辑**（公开画廊的视觉与交互）保持不动即可。

> 启用 R2 是独立动作，见 §C——升级不需要 R2，R2 也不需要重新部署。

### B. 日常使用（三种场景）

**场景 1：电脑上整理照片 → 走 SMB（你的主场景）**

```bash
# 把照片拷进 NAS 的 data/originals/（拖拽即可，无需命令）
```

然后在浏览器打开 `https://你的域名/admin`，点一次「**立即同步**」，几秒到几分钟后照片出现在画廊。

> **相比现在的流程，唯一变化是：不用再进终端敲 `docker compose run --rm sync`，改成在网页上点一下。**
> 照片仍然走 SMB 拷贝（这条链路本来就是顺畅的），管理端不接管你的整理习惯。

**场景 2：手机直接上传（无 SMB 的场景）**

1. 浏览器打开 `https://你的域名/admin`，输入口令登录
2. 选照片上传，看进度条走完
3. 上传完成后**不会自动同步**（见 §0.6 决策 C2）——界面会显示「待同步 N 张」
4. 确认可以展示了，点一次「立即同步」，刷新首页即可看到

**场景 3：删除照片**

1. `/admin` 里选中照片 → 删除
2. 程序把原图移入 `data/.trash/`（软删除，可恢复）
3. **不会自动同步**（见 §0.6 决策 C5）——照片此时**仍在公开画廊显示**，标记为「待删除」
4. 想让它在网站上消失，点一次「立即同步」
5. 删错了想恢复：把 `data/.trash/` 里的文件移回 `data/originals/`，再同步一次即可
6. 确认不要了：**手动删掉 `data/.trash/` 里的文件**（不会自动清理，见 §12 #3）

### C. 启用 R2 加速（可选，随时可做）

```bash
# 1. 在 Cloudflare 建 R2 桶，建 API Token（Object Read & Write）
# 2. 给桶绑定自定义域名（如 img.example.com），不要用 r2.dev（见 §7.2）
# 3. 把配置追加到 .env
cat >> .env <<'EOF'
FRAMEFOLIO_S3_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com
FRAMEFOLIO_S3_REGION=auto
FRAMEFOLIO_S3_BUCKET=framefolio
FRAMEFOLIO_S3_ACCESS_KEY_ID=xxx
FRAMEFOLIO_S3_SECRET_ACCESS_KEY=xxx
FRAMEFOLIO_S3_PUBLIC_BASE_URL=https://img.example.com
EOF

# 4. 重启使配置生效
docker compose -f compose.image.yml up -d gallery
```

然后在 `/admin` 里：

1. 点「上传到 R2」→ 补传全部派生图（首次可能几分钟，看照片数量）
2. 点「切换访问源」→ 选 `r2`
3. 刷新首页 → 图片全部走 CDN

**回退**：把访问源切回 `local` 即可，本地链路完全独立，**不受 R2 影响**。

### D. 运维

```bash
# 看日志
docker compose -f compose.image.yml logs -f gallery

# 手动同步（逃生通道，随时可用）
docker compose -f compose.image.yml run --rm sync

# 备份（data 现在可写，备份语义见 §0.6 C8）
#   必备份：data/originals/
#   建议一并备份：data/photos.json、data/.state/
#   可不备份：data/generated/（可重新生成）、data/.trash/（软删除区）
```

### E. 明确不变的部分

- **公开画廊的访问方式完全不变**：同一个域名、同一个端口、不登录即可浏览
- **`/media/*` 与 `/api/photos` 的对外行为不变**（前端零改动）
- **手动 CLI 始终保留**（§5.4），与 Web 触发共用同一把锁
- **本地照片访问能力始终保留**，R2 只是可选的另一个源

### 0.6 已确认的决策

> 本节编号用 **C1–C8**（Confirmed），与 §3 的「关键设计决策 D1–D11」是**两套独立编号**，避免混淆。

| #      | 决策                                | 结论                                                                                                                                                                                                                                             |
| ------ | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **C1** | 新版镜像怎么交付？                  | **推送到 Docker Hub**（已确认）。NAS 上不本地构建（Pentium 构建 Nuxt 很慢）                                                                                                                                                                      |
| **C2** | Web 上传后是否自动触发同步？        | **否**（已确认）。上传只负责落盘，**同步是显式的用户动作**。这取消了整套去抖/队列机制，见 §6.4                                                                                                                                                   |
| **C3** | `/admin` 是否在反代层再加一层防护？ | **建议是**（Cloudflare Access 或 Basic Auth）。非阻塞项，可后补                                                                                                                                                                                  |
| **C4** | 后台页面视觉投入                    | **按正常后台管理页做**，用现有令牌与手写 CSS，不引入 UI 组件库；**不做**视觉稿与品牌打磨，但**必须保证移动端可用**                                                                                                                               |
| **C5** | 删除后是否自动同步？                | **否**（已确认）。上传与删除都只是**改动 `data/originals/` 里的文件**，都要等用户按同步才生效                                                                                                                                                    |
| **C6** | 是否做定时轮询自动同步？            | **否**（已确认砍掉）。触发入口只保留「立即同步」按钮与 CLI 两个显式动作（见 §5）                                                                                                                                                                 |
| **C7** | 是否兼容旧版索引格式？              | **不兼容**（已确认）。本项目仅一个使用者，允许破坏性更新；**当新项目做**。代价是升级后首次同步会重建全部缩略图（一次性）。**但旧版的展示逻辑（公开画廊视觉与交互）保持不动**                                                                     |
| **C8** | `data` 变为可写后，备份语义？       | **必备份 `data/originals/`**（唯一数据源）；建议一并备份 `data/photos.json` 与 `data/.state/`；**可不备份** `data/generated/`（可重新生成）与 `data/.trash/`（软删除区）。注意 `data/photos.json` 已可从 `originals/` 重建，因此它不是必需备份项 |
| **C9** | 管理端的渲染方式与收录策略？        | **管理端做成 SPA**（`routeRules: { '/admin/**': { ssr: false } }`），**公开画廊保持 SSR 不变**；同时 `robots.txt` 与响应头双重禁止收录 `/admin`。理由见 §6.7                                                                                     |

**关于 C3 的补充**：管理端不在公开页面加入口，需手动输入 `/admin`（已确认）。这是减少暴露面的做法，但**不能替代鉴权**——应用层口令鉴权仍必须做。

**关于 C2 + C5 + C6 的统一心智模型（重要）**：

> **上传 = 往 `originals/` 加文件；删除 = 从 `originals/` 移走文件。两者都不触发同步。**
> **想让网站在变化，按一次同步按钮即可（生成图片 + 更新索引同时完成）。**

同步按钮做的事就一件：**跑一遍同步管线**（生成缩略图、写索引、清理旧图）。带来三条一致的行为：

| 行为 | 按下同步按钮前                             | 按下同步按钮后 |
| ---- | ------------------------------------------ | -------------- |
| 上传 | 公开画廊**不变**，照片标记为「新增」       | 出现在公开画廊 |
| 删除 | 公开画廊**仍显示**该照片，标记为「待删除」 | 从公开画廊消失 |
| 修改 | 公开画廊**仍是旧图**，标记为「变更」       | 更新为新图     |

**这要求界面把「待同步」做得足够醒目**——否则用户可能忘记按同步，导致"删了但还挂在网上"。这是该模型唯一需要刻意设计的地方（见 §6.4）。

## 1. 痛点分解

### 1.1 已确认的事实

- 部署方式：NAS + Docker（`compose.image.yml`）
- 数据卷是**宿主机 bind mount**（`./data:/app/data`），因此可以直接通过 SMB 把照片拷进 `data/originals/`
- 相册网页**已实现代理访问**，外网可正常浏览
- 「外网访问 NAS 环境」指的是**内网终端**（用于执行命令），终端虽也可代理访问，但操作繁琐
- 照片入口：**通过 SMB / 文件共享拷贝**
- 期望能力：Web 管理（上传、转换、删除）+ R2/CDN 加速 + 全局访问源切换

### 1.2 痛点与对策

| 痛点                     | 真实成因             | 对策                                                 | 成本 |
| ------------------------ | -------------------- | ---------------------------------------------------- | ---- |
| 每次同步都要进终端敲命令 | 处理只能由 CLI 触发  | **管理端「立即同步」按钮**（Web 触发，复用同一管线） | 低   |
| 外网操作 NAS 终端繁琐    | 缺少 Web 入口        | Web 管理端                                           | 中   |
| 访问图片慢               | 图片存在 NAS，无 CDN | R2 存储 + 全局源切换                                 | 中高 |

> **关于「外网可达」的澄清**：这不构成阻塞项。相册网页已通过代理可达，终端也可代理访问，只是繁琐。因此本方案的前提是成立的，Web 管理端要解决的是**操作便利性**，而非连通性。

> **关于「不再需要终端」的边界**：CLI **仍然保留**（批量导入、故障恢复、脚本化时仍有用，见 §5.4），但**日常使用不再需要它**——SMB 拷完照片后在网页点一下按钮即可。这是与现状最本质的区别。

## 2. 与现有能力的关系

### 2.1 无冲突的部分（应完整保留）

- `scripts/lib/gallery-sync.ts` 的增量同步、EXIF 提取、双规格 WebP、失败重试
- 索引原子替换（`photos.json.tmp` → rename）与失效生成物清理
- 指纹命名 `<id>-<revision>-<variant>.webp`
- 媒体路由的路径穿越双重防护（白名单正则 + resolve 前缀校验）
- `app/utils/gallery-layout.ts` 纯函数布局算法
- `shared/` 契约层与 `data/originals` 为唯一数据源的设计

### 2.2 必须有意打破的约束

`DEV.md` 有三条约束是为「无管理端」而设计的，本次必须调整：

| 约束                       | 位置                                            | 调整                                           |
| -------------------------- | ----------------------------------------------- | ---------------------------------------------- |
| 请求链路禁止 sharp / exifr | `DEV.md:135-141`                                | 允许**任务进程**使用；API 处理器仍不得直接加载 |
| `data` 只读挂载            | `docker-compose.yml:27`、`compose.image.yml:12` | 改为可写（Web 上传需要写入 `originals/`）      |
| 处理只能由 CLI 完成        | `DEV.md:141`                                    | 可由 Web 触发，但复用同一套管线                |

> `tests/unit/gallery-runtime.test.ts:97` 的「运行时依赖边界」测试**不删除，改为改写**：从「server 下任何文件都不得出现 sharp」（现断言在 `:107`）改为「仅同步任务进程可加载 sharp，API 处理器必须经队列派发」。这是本次重构的重要契约，须显式维护。

### 2.3 R2 与指纹命名天然契合（而非冲突）

`<id>-<revision>-<variant>.webp` 是内容寻址命名，配合现有 `immutable` 长缓存，**正是 CDN 最理想的形态**：

- 原图或处理参数变化 → revision 变化 → 文件名变化 → **无需 CDN 刷新**
- 切换访问源**不需要重新处理图片**，因为文件名完全相同，只是 base URL 不同

但存在一处**真实紧耦合**需要解开：索引把 URL 烘焙进了数据模型，且校验强制以 `/media/` 开头：

```ts
// scripts/lib/gallery-sync.ts:559  →  thumbnail: `/media/${filename}`
// server/utils/gallery-index.ts:123 →  expectedPrefix = `/media/${id}-${revision}-`
```

**解法：索引内部只存「存储键」（文件名），URL 在 API 读取时按当前源拼装。**
公开 API 仍返回拼装好的 URL，因此**前端零改动**。

### 2.4 新引入的风险

| 风险       | 说明                                   | 缓解                                 |
| ---------- | -------------------------------------- | ------------------------------------ |
| 安全面扩大 | `data` 可写 + 管理端暴露公网           | 强鉴权、限流、上传校验、反代二次防护 |
| 读写一致性 | 对象存储无事务，可能产生孤儿对象或缺失 | 幂等清理 + 逐张远端状态 + 完整性检查 |
| 原生崩溃   | libvips 处理损坏图片可能段错误         | 独立子进程隔离（见 §4.1）            |

## 3. 关键设计决策

| 编号 | 决策           | 选择                                                                                         | 理由                                                                                                                                                                                                                                    |
| ---- | -------------- | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1   | 同步执行位置   | **独立子进程**，非请求内同步                                                                 | libvips 对损坏/截断图片可能原生崩溃，子进程崩溃不会拖垮 Web 服务；且完全复用现有 CLI 代码路径，无 Nitro 打包原生依赖的风险                                                                                                              |
| D2   | 上传传输方式   | **流式 `PUT` 单文件**，非 multipart                                                          | h3 的 `readMultipartFormData` 会把整个请求读入内存，大图必然 OOM；改用 `getRequestWebStream` 管道落盘，内存恒定，且无需新增依赖                                                                                                         |
| D3   | 进度推送       | **前端轮询任务状态接口**，SSE 作为后续增强                                                   | 反代/隧道对 SSE 支持不一，前端轮询简单可靠。注意这是**前端查任务进度**，与「定时轮询自动同步」无关（后者已砍掉，见 §5）                                                                                                                 |
| D4   | 索引结构       | **schema v2**：内部存存储键，公开 API 返回 URL                                               | 解开 URL 与数据模型的耦合，使换源成为纯读时行为                                                                                                                                                                                         |
| D5   | 存储源切换语义 | **全局开关**（服务端配置）                                                                   | 全体访客 URL 一致，CDN 缓存命中率最高，实现最简                                                                                                                                                                                         |
| D6   | 对象存储协议   | **S3 兼容**（`@aws-sdk/client-s3`）                                                          | 已确认使用 **Cloudflare R2**；R2 提供 S3 兼容 API（`region: auto`，endpoint 形如 `https://<account-id>.r2.cloudflarestorage.com`）。同一实现亦可对接阿里云 OSS / MinIO / AWS，并可用 MinIO 本地测试。**不引入 `ali-oss`**，避免厂商锁定 |
| D7   | 访问源解析     | **逐张判定**，非全局盲切                                                                     | 若某张尚未上传，自动回退本地，避免整站白图（见 §7.3）                                                                                                                                                                                   |
| D8   | 删除语义       | **软删除**到 `data/.trash/`，**不自动清理**                                                  | 实现成本低（仅 move 而非 rm），且作品集误删代价高。不设自动清理任务 = 更少代码与更少误删风险；`.trash/` 不影响扫描（不在 `originals/` 内）                                                                                              |
| D9   | 管理端启用条件 | **未配置口令则整体禁用**                                                                     | 安全默认，避免误部署裸奔                                                                                                                                                                                                                |
| D10  | 同步触发方式   | **仅两个显式入口**：管理端按钮 / 命令行 CLI。**不做定时轮询**                                | 契合「按下按钮才生效」的模型，行为可预测；省去 SMB 半截文件防护等轮询特有逻辑（已确认砍掉轮询）                                                                                                                                         |
| D11  | 自定义域名     | **部署时建议使用自定义域名**（可获得 CDN 缓存；`r2.dev` 仅为开发用途，不受缓存且有速率限制） | 这是**运维建议**而非代码约束：`FRAMEFOLIO_S3_PUBLIC_BASE_URL` 只是字符串前缀，填什么代码行为都相同（见 §12.1）                                                                                                                          |

## 4. 目标架构

### 4.1 进程与容器模型

保持**单容器**，不引入 worker / queue / 数据库。

```text
┌─ framefolio 容器 ────────────────────────────────┐
│                                                  │
│  Nuxt / Nitro (主进程)                            │
│   ├── GET /api/photos        ← 公开只读           │
│   ├── GET /media/:filename   ← 本地源图片          │
│   └── /api/admin/*           ← 鉴权后：上传/删除/  │
│                                 状态/切换源        │
│                                                  │
│  同步任务运行器（子进程 spawn）                     │
│   └── node --import tsx scripts/gallery-sync.ts  │
│        · 独占锁，同一时刻仅一个任务                 │
│        · JSONL 输出进度 → 由主进程收集              │
│        · 崩溃不影响 Web 服务                       │
│        · 触发入口仅两个：管理端按钮 / CLI           │
│          （不做定时器、不做上传后自动触发）          │
└──────────────────────────────────────────────────┘
```

为什么是子进程：sharp / libvips 是原生模块，处理**损坏或截断的图片**时可能触发不可捕获的段错误。请求内同步会让 Web 服务一起崩溃；子进程则只让本次任务失败。考虑到照片经 SMB 拷入（存在半截文件的可能），这个隔离有实际价值。

#### 4.1.1 「单容器 / 双容器」到底指什么

这里说的**不是**数据库或消息队列——从头到尾只有 Nuxt 一个应用。区别仅在于：**同一个应用要不要拆成两个服务跑、数据卷给不给写权限。**

先看现状。你现在的 `docker-compose.yml` 其实**已经是两个服务**，只是都来自同一个镜像：

```yaml
gallery: # 对外提供网站，data 只读
  volumes: [./data:/app/data:ro]
sync: # 只在手动执行时运行，data 可写
  profiles: [tools]
  volumes: [./data:/app/data]
```

关键点：**`gallery` 是只读的**。所以即使公开的网站被攻破，攻击者也无法修改或删除你的原图——这是一个真实的、现在就有用的安全边界。

而「上传 / 删除」功能**必须写 `data`**。于是问题变成：**这个写权限给谁？**

|                      | 方案 A：单容器                                    | 方案 B：双容器                                                     |
| -------------------- | ------------------------------------------------- | ------------------------------------------------------------------ |
| 结构                 | 把 `gallery` 改为可写，管理端和公开站点同一个服务 | 保留 `gallery` 只读；新增 `admin` 服务可写，两者共享同一 `data` 卷 |
| compose 变化         | 删掉 `read_only: true`（一行）                    | 多一个 service 块 + 反代把 `/admin` 指过去                         |
| 端口                 | 1 个（3123）                                      | 2 个（如 3123 公开、3124 管理），或用反代按路径分流                |
| 内存占用             | 1 个 Node 进程                                    | **2 个 Node 进程**（Nuxt 常驻约 100–200MB）                        |
| 被攻破的影响         | 攻击者可写 `data`（能删原图）                     | 管理服务被攻破才能写；公开服务仍无法写                             |
| 管理端能否不暴露公网 | 与公开站点同源，只能靠鉴权                        | **可以完全不暴露**，仅内网/VPN/Cloudflare Access 可达              |
| 部署复杂度           | 最低                                              | 中（多一个服务与路由规则）                                         |
| 适合                 | 单用户 NAS、追求简单                              | 在意纵深防御、NAS 内存充足                                         |

**方案 B 并不是什么新架构**——它只是把现有的 `sync` 服务扩展成一个常驻的 `admin` 服务，复用你已经在用的 `ro` / `rw` 双挂载模式。

**两者共享同一 `data` 卷不会有冲突**：`gallery` 每次请求都重新读 `photos.json`，所以 `admin` 同步完成后，公开站点刷新即可看到新照片（这正是现有「同步后不用重启容器」的机制）。同步锁文件在共享卷上，也不会出现两个任务同时对写。

**本方案默认选 A**，理由是你的核心诉求是「简化部署」，而 A 只改一行、不加进程、不加端口。安全上以**反代层加固**补齐：

> 在 Cloudflare / Nginx 上对 `/admin` 路径再加一层认证（如 Cloudflare Access、Basic Auth），或直接限制来源 IP。这样即便应用层鉴权被绕过，仍有一道外部防线。

**何时该换成 B**：如果你将来把管理端暴露在公网且不放心单一鉴权，或 NAS 内存充裕、愿意用多一个进程换取「公开服务永远无法写原图」的硬隔离。由于两个方案**共用同一份代码与迁移路径**，A → B 是纯 compose 层改动，**随时可切，不需要重构**。

### 4.2 目录布局

```text
data/
├── originals/          # 原图（唯一数据源；Web 上传最终落此）
├── generated/          # 派生图（thumbnail / preview）
├── incoming/           # 上传暂存（新）；校验通过后移入 originals
├── .trash/             # 软删除区（新）
├── .state/             # 运行时状态（新）
│   ├── jobs.json       # 任务账本：状态、进度、摘要
│   └── sync.lock       # 防并发锁
└── photos.json         # 索引（schema v2）
```

`incoming` 的必要性：上传先落暂存区，完成 magic-byte 校验后再原子移入 `originals`，避免扫描器把半截文件当作有效照片处理。

### 4.3 索引 schema v2

```ts
interface PhotoIndexItem extends GalleryPhoto {
  /** 存储键：仅文件名，不含 base URL */
  storage: {
    thumbnail: string
    preview: string
  }
  /** 本地原图状态，用于增量判定 */
  source: {
    size: number
    mtimeMs: number
    revision: string
  }
  /** 远端副本状态；缺失 = 尚未上传，读取时回退本地 */
  remote?: {
    provider: 's3'
    revision: string
    uploadedAt: string
  }
}
```

关键点：

- `GalleryPhoto`（公开 API 类型）**保持不变**，`thumbnail` / `preview` 仍是完整 URL，由 `server/utils/gallery-index.ts` 在读取时拼装 → **前端零改动**
- `remote.revision !== source.revision` 即视为需重新上传，天然自愈
- **派生图文件名完全不变**：索引里记的 `<id>-<revision>-<variant>.webp` 与现在磁盘上的文件同名，R2 对象键也用它。**换源不需要重新处理任何图片**，只是前缀不同

**关于 `pipelineVersion`（修正）**：此前本文档写过「升到 3，触发一次全量重生成（命名与结构变化的正常代价）」——**这个说法不准确**：命名与结构都没有变化，派生图本身依然有效，因此**不需要因为换源而升 `pipelineVersion`**。

真正会让首次同步重建全部缩略图的原因只有一个：**索引换成了新格式，新版读不出旧索引里的缓存，只能从原图重建**（见 §0.5 A）。这是"索引格式变更"的一次性代价，与派生图命名无关，也不需要靠 `pipelineVersion` 来表达。

### 4.4 存储源解析

```ts
resolvePhotoUrl(storageKey, variant, { source, remote, currentSource })
// currentSource = 'local' → /media/<key>
// currentSource = 'r2'    → <s3PublicBaseUrl>/<key>   （仅当 remote.revision === source.revision）
//                          否则回退 /media/<key>
```

配置项（均走 `runtimeConfig`，服务端私有）：

| 变量                                                 | 说明                                                                                           |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `FRAMEFOLIO_STORAGE_SOURCE`                          | `local` \| `r2`，默认 `local`                                                                  |
| `FRAMEFOLIO_S3_ENDPOINT`                             | S3 兼容端点；R2 为 `https://<account-id>.r2.cloudflarestorage.com`                             |
| `FRAMEFOLIO_S3_REGION`                               | R2 填 `auto`                                                                                   |
| `FRAMEFOLIO_S3_BUCKET`                               | 桶名                                                                                           |
| `FRAMEFOLIO_S3_ACCESS_KEY_ID` / `_SECRET_ACCESS_KEY` | R2 API Token 生成的凭据                                                                        |
| `FRAMEFOLIO_S3_PUBLIC_BASE_URL`                      | 公开访问基址**字符串前缀**；填自定义域名、`r2.dev` 或 MinIO 地址均可，代码行为相同（见 §12.1） |
| `FRAMEFOLIO_S3_PREFIX`                               | 对象前缀，便于同桶多站                                                                         |
| `FRAMEFOLIO_ADMIN_PASSWORD`                          | 管理端口令；**未设置则管理端禁用**                                                             |
| `FRAMEFOLIO_SYNC_CONCURRENCY`                        | 同步并发。**默认 `1` = 保持现有串行行为**；仅在确认 NAS 有余力时才调高（见 §9.5）              |

> 变量统一用 `S3_` 前缀而非 `OSS_`，因为实际后端是 R2；同一套配置可指向任何 S3 兼容服务。

## 5. 同步触发方式（最高优先级）

### 5.1 只有一个来源：用户按一下

**同步的触发入口只有两个，都是显式动作：**

| 入口                       | 用途       | 何时用                                         |
| -------------------------- | ---------- | ---------------------------------------------- |
| **管理端「立即同步」按钮** | 日常使用   | SMB 拷完照片 / 手机上传完 / 删除完 → 点一下    |
| **命令行 CLI**             | 批量与逃生 | 首次全量导入、Web 起不来时修复、脚本化（§5.4） |

**不做定时轮询，也不做「上传/删除后自动触发」。** 这是已确认的决定（§0.6 C2 / C5 / C6）。

这个决定的实际效果：**你原来的痛点「必须进终端敲命令」被消除了**——日常工作流变成「SMB 拷照片 → 网页点一下按钮」，全程不碰终端。而 CLI 作为逃生通道继续存在。

> 为什么不做轮询：既然你确认了「真实落实要我按下那个同步按钮」，轮询就与这个模型冲突——开了轮询后，「待同步」状态会自己变化，你反而不知道网站当前是什么状态。同时轮询还需要额外的半截文件防护（见 §5.3）。为低频使用场景增加这些复杂度不划算。

### 5.2 实现

**已验证可行**：从 Node 主进程 `spawn` 子进程执行 `scripts/gallery-sync.ts` 已实测成功（退出码 0，正确产出 2 个派生图与索引）。这是「Web 触发 sync」的技术前提，已确认成立。

- 管理端按钮 → 派发一次加锁的同步任务（子进程 + `jobs.json` 账本记录进度与摘要）
- 无变更时直接跳过（扫描后 summary 全为 0），不做任何处理
- 无定时器、无后台常驻任务：不点按钮就什么都不发生
- **必须加全局锁**：这是修复 §7.6 所记录的已存在并发缺陷的主要手段，而非单纯的资源优化

### 5.3 为什么不需要「SMB 半截文件防护」

照片是通过 SMB 拷入 bind mount 的 `data/originals/`，拷贝大图可能耗时数秒到数分钟。**如果**引入定时轮询，就可能扫到不完整文件——sharp 报错（可被现有错误处理接住），但会在拷贝完成前每轮都报一次，污染日志并浪费 CPU。为此原本设计过「静置时间判定」过滤。

**砍掉轮询后，这个风险随之消失，该过滤逻辑也不需要了：**

| 场景                 | 是否会读到半截文件 | 原因                                                                                                     |
| -------------------- | ------------------ | -------------------------------------------------------------------------------------------------------- |
| 手动点按钮（本方案） | **不会**           | 人不会在拷贝中途点同步；真点了也只是本次报错，再点一次即可                                               |
| 定时轮询（已砍掉）   | 会                 | 定时器不看人的操作时机                                                                                   |
| Web 上传             | **不会**           | 上传先落 `incoming/`，**magic-byte 校验通过后才原子移入 `originals/`**（§4.2），扫描器永远看不到半截文件 |

> 因此这是**砍掉轮询带来的额外收益**：少写一段只有轮询才需要的管线逻辑。

### 5.4 保留手动 CLI 与子进程的性能对比（已实测）

**手动 CLI 必须保留**，且它**不会比子进程慢**。这里有一个常见误解需要澄清。

实测对比同一份 25 张全量任务：

| 执行方式                           | 耗时       |
| ---------------------------------- | ---------- |
| 进程内直接调用 `runGallerySync()`  | **8.01 s** |
| 子进程 `spawn`（管理端采用的方式） | **7.95 s** |

**差异在测量噪声范围内 → 「在进程内跑会更快」是误解。**

原因有二：

1. **`spawn` 的开销极小**：实测额外开销仅约 **40 ms**（纯 node 启动 0.03 s，`node --import tsx` 0.05 s，加载管线的 `runGallerySync` 模块 0.07 s）。而处理一张 42 MP 图就要 490 ms——启动开销占比不到 0.5%。
2. **真正的耗时全在图片处理**：`spawn` 只是创建进程，图片处理本身无论在父进程还是子进程都在**同样的 CPU 核心**上跑，工作量一模一样。

最常用的「无变化增量」场景更说明问题：

| 方式                          | 耗时       |
| ----------------------------- | ---------- |
| 手动 CLI（含启动 + tsx 转译） | **0.08 s** |
| 进程内调用（省掉启动）        | **0.08 s** |

**完全无法区分**——因为 0.08 s 里绝大部分是磁盘 `stat`，不是启动。

> 若追求极致，唯一能省的是 tsx 的运行时转译开销（约 40 ms）。可通过在 Docker 构建阶段预编译为 JS 消除，但**收益仅几十毫秒，不值得为此增加构建复杂度**。

**因此性能不应成为「保留手动 CLI」的考虑因素。** 保留它的真正理由是：

- **批量导入**：首次导入数百张时，在终端执行并观察输出比在网页上等更可靠
- **故障恢复**：Web 服务起不来时，仍能修复索引与生成图
- **CI / 脚本化**：自动化流程需要一个可直接调用的命令入口
- **排查同步问题**：终端能看到完整的警告与错误明细

**关键约束：CLI 与 Web 触发的同步必须共用同一把锁**（`data/.state/sync.lock`）。否则「在网页点了按钮」恰逢「在终端敲了命令」时，就会命中 §7.6 记录的并发缺陷，导致派生图缺失。这是保留 CLI 时必须一并处理的问题——**不是简单地保留命令即可**。

### 5.5 删除语义（已实测验证）

**「软删除」只需把原图移出 `originals/`，然后跑一次同步即可。** 管线会自然处理后续，无需新增删除逻辑。

实测流程与结果：

| 步骤                                            | 实测结果                                                                                                          |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 把原图从 `originals/` 移入 `.trash/`，执行 sync | `deleted 1`，退出码 0；索引从 1 张 → 0 张；`generated/` 中该照片的 2 个派生图**被自动清理**（因为已不被索引引用） |
| 再把原图移回 `originals/`，执行 sync            | `added 1`，索引恢复 1 张，派生图重新生成 → **可完整恢复**                                                         |

由此确定：

- **索引更新**是自动的，无需手写
- **`generated/` 派生图**由现有清理逻辑自动回收，无需额外处理
- **原图**在 `.trash/` 与 R2 上**都仍然存在**（R2 上的对象需显式删除，否则成为孤儿）
- 恢复时 `revision` 会重新计算，**文件名可能变化**（因为 `mtime` 变了）→ 恢复后 R2 上需重新上传，旧的成为孤儿

**因此删除分为两步，第一步即时、第二步由同步落实：**

| 步骤 | 时机                 | 做什么                                                                                         |
| ---- | -------------------- | ---------------------------------------------------------------------------------------------- |
| 1    | **点删除时立即**     | 原图 `originals/` → `.trash/`（软删除，可恢复）。此时公开画廊**仍显示**该照片                  |
| 2    | **用户按同步按钮时** | 索引摘除该照片、清理 `generated/` 派生图、删除 R2 对象（失败则记为待清理项，下次同步幂等重试） |

> 与上传完全对称：上传是往 `originals/` 加文件、删除是从 `originals/` 移走文件，**两者都在等用户按一次同步**（见 §6.4）。

**唯一需要手动的是「彻底销毁」**：`.trash/` 里的原图不会自动删（这是刻意的，见 §12 #3）。你确认不再需要时，直接删掉 `.trash/` 里的文件即可——它就是个普通目录，删了不影响网站。

## 6. Web 管理端

### 6.1 功能范围（本期）

- **上传**：拖拽/选择多文件，逐文件进度、失败重试；**主要价值在手机浏览器直传**（SMB 已顺畅的场景下，桌面端上传属锦上添花）
- **同步**：上传/删除都只改 `originals/`，需手动按「立即同步」才生效（§6.4）。管理端展示「待同步：新增 N · 变更 N · 待删除 N」
- **转换**：触发增量同步；支持「单张重新生成」与「全部重新生成」
- **删除**：软删除到 `.trash/`，联动清理派生图与 R2 对象
- **状态**：当前任务进度、上次同步摘要（新增/更新/跳过/删除/失败）、日志尾部
- **存储**：当前访问源展示与切换、R2 完整性统计与一键补传

### 6.2 明确不做

- 照片标题 / 描述文案（本次未选，会扩大数据模型改动）
- 相册分组 / 手动排序 / 精选封面（建议单独一期）
- 多用户、角色权限

### 6.3 视觉

**定位：普通、好用的后台管理页，不做视觉稿、不做品牌打磨，也不刻意简陋。**

- 复用现有语义色变量（`--gallery-*`）、字体栈与动效曲线 → **深色模式自动生效**，无需额外适配
- 手写 scoped CSS；**不引入 UI 组件库**（理由见 §6.5）
- 允许表格、表单、进度条等工具型控件；照片列表不用大图卡片
- **不得污染公开画廊的视觉基线**：公开页面（`app/pages/index.vue`、`Header`）**零改动**
- **移动端可用是功能底线，不是可选打磨**：现有断点 `48rem` 以下，表格退化为卡片式列表行，点击目标 ≥44px。手机直传是上传功能的主要价值，横向溢出即等于功能失效

### 6.4 上传与删除都不自动同步（已确认）

**决定：上传和删除都只是改动 `data/originals/` 里的文件，不触发同步。要看到效果，由用户按一次同步按钮。**

#### 先明确：同步就是一件事

`runGallerySync` 是**单个操作**，内部依次完成（`gallery-sync.ts:179-247`）：

```text
扫描 data/originals/
  → 生成缩略图与预览图（写 data/generated/）
  → 写 data/photos.json
  → 清理不再被引用的旧图
```

**生成缩略图和更新索引是同一个操作的两步，不是两件事。** 所以「同步」既产出图片、也让网站更新——不存在"先同步图片、再另外发布"的说法。

（此前文档用了「同步即发布」「意向」等说法，容易让人以为同步只是一次"确认"动作、图片是另外生成的。这是表述问题，这里改回直白说法。）

#### 那上传和删除各自做什么

| 操作     | 对 `data/originals/` 的影响               | 网站什么时候变 |
| -------- | ----------------------------------------- | -------------- |
| **上传** | 新增文件                                  | 同步之后       |
| **删除** | 文件移入 `data/.trash/`（软删除，可恢复） | 同步之后       |
| **修改** | 替换文件                                  | 同步之后       |

**三者都是"改了原图目录"，都要等同步才生效。**

#### 为什么不做成"上传完自动同步"

自动同步需要额外处理：一场上传要触发几次、什么时候算传完、多个同步撞在一起怎么办。这些机制此前设计过（去抖、队列排空、静置延迟），**既然你愿意手动按一次按钮，这些就全都不需要了**：

| 原需要实现                   | 现在   |
| ---------------------------- | ------ |
| 上传队列计数                 | 不需要 |
| 静置延迟、最长等待上限       | 不需要 |
| 「待执行」标记与补跑         | 不需要 |
| 「等待秒数」「窗口张数」设置 | 不需要 |

**同步的触发入口只剩两个，全部是明确动作：管理端「立即同步」按钮 / 命令行 CLI。** 两者共用 `sync.lock`，不会互相打架。

#### 「待同步」状态如何呈现（已实测可行）

因为不自动同步，界面需要告诉你「有些改动还没生效」。检测成本极低——复用现有增量逻辑的 stat 比对即可：

| 实测（1000 张照片的库）          | 结果      |
| -------------------------------- | --------- |
| 检测待同步项（新增/变更/待删除） | **64 ms** |
| 首次全量 1000 张                 | 11.71 s   |
| 增量无变化                       | 0.036 s   |
| 索引体积                         | 389 KB    |

UI 呈现：

```text
待同步：新增 3 · 变更 0 · 待删除 1        [ 立即同步 ]
```

并在具体照片行上标记「新增」「已变更」「待删除」，让你清楚哪些改动还没生效。

#### 必须提醒：删除要同步后才从网站消失

这是"不自动同步"最需要注意的一点：

- **上传**未同步 → 只是照片还没出现，无风险
- **删除**未同步 → **照片仍在公开画廊显示**（只是原图已移入 `.trash/`）

所以界面必须把「待同步」做得醒目（上面第 4 条），删除确认时也要明确告知：「已移入回收站，**需点击同步后才会从网站移除**」。

### 6.5 为何不引入 UI 组件库

| 理由                | 说明                                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------ |
| 已有原生 `<dialog>` | `PhotoViewer.vue:189` 已在用；删除确认复用同一模式，**零依赖**                             |
| 所需控件极少        | 输入框、按钮、表格、进度条、开关、单选、拖拽区——均为原生元素 + 少量 CSS 可覆盖             |
| 库的移动端表现差    | Element Plus / Ant Design Vue 面向 PC 后台，**表格在窄屏体验差**，而移动端上传正是核心场景 |

### 6.6 哪些可配、哪些写死

**原则：只暴露用户真正会想调的；凡影响正确性的，一律写死不给开关。**

> **注意：不存在「同步设置」这一组配置。** 没有轮询间隔、没有自动同步开关——同步只由按钮和 CLI 触发，无参数可调。

#### 写死（不提供设置）

| 参数                                | 固定值 | 为何不给设置                                           |
| ----------------------------------- | ------ | ------------------------------------------------------ |
| **串行执行**（同一时刻仅 1 个同步） | 强制   | **正确性修复**，不是偏好。关掉会复现 §7.6 的派生图缺失 |
| **`sync.lock` 锁**                  | 强制   | 管理端按钮 / 命令行 CLI 共用，无开关                   |
| 临时文件唯一化                      | 强制   | 纵深防御（`pid` + 随机串；清理只针对死进程残留）       |

#### 关于「去抖的设置」：问题已消失

| ------------------ | -------------------------- |

| 窗口张数           | **已取消**                 |
| 上传队列排空判据   | **已取消**                 |
| 上传后自动同步开关 | **已取消**（固定为不触发） |
| 定时轮询间隔       | **已取消**（不做轮询）     |

**当前同步的触发来源只有两个，全部是明确动作：**

1. 管理端点「立即同步」
2. 命令行 CLI

**这也正是这个设计更好的地方：触发点从「隐式后台行为」变成了「两个显式入口」，既不需要去抖，也不会有并发风暴。**

### 6.7 管理端为 SPA，公开画廊保持 SSR（已确认）

**决定：管理端按 SPA 渲染（客户端渲染），公开画廊的 SSR 完全不动。**

配置（`nuxt.config.ts`）：

```ts
routeRules: {
  '/admin/**': { ssr: false },
  '/api/admin/**': { headers: { 'X-Robots-Tag': 'noindex, nofollow' } }
}
```

> 已核对 Nuxt 4.5.2 / Nitropack 2.13.4 的类型定义，`routeRules` 支持 `ssr` 与 `headers`，上述写法成立。

**为什么管理端适合 SPA：**

| 理由           | 说明                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------ |
| 不需要 SEO     | 管理页只给你自己看，没有搜索引擎收录需求                                                   |
| 不依赖首屏内容 | 打开后要等接口返回照片列表，SSR 预渲染的静态骨架没有实质价值                               |
| 少一条渲染路径 | 管理端的状态（登录态、进度、待同步数）全是运行时数据，SSR 只会增加一套需要维护的服务端分支 |

**明确不受影响的部分**（这是硬约束）：

- **公开画廊保持 SSR**：`app/pages/index.vue` 的渲染方式不变，首屏仍有服务端输出的内容
- **公开 API 与媒体路由不变**：`/api/photos`、`/media/*` 都是 Nitro 服务端路由，与页面渲染模式无关
- **`app/pages/index.vue` 与 `GalleryHeader` 零改动**（沿用 §6.3 的约束）

**禁止收录（两层，互为补充）：**

| 层                                       | 做法                                       | 可靠性                           |
| ---------------------------------------- | ------------------------------------------ | -------------------------------- |
| `public/robots.txt`                      | `Disallow: /admin`、`Disallow: /api/admin` | 依赖爬虫自觉，是**约定**不是强制 |
| 响应头 `X-Robots-Tag: noindex, nofollow` | 由 `routeRules` 注入                       | 更可靠，但同样依赖爬虫遵守       |

> **必须说清楚：这两层都不是访问控制。** 它们只防止被搜索引擎收录，**任何人都仍可直接访问 `/admin` 并看到登录页**。真正的防线是 §4.6 的口令鉴权，以及 C3 建议的反代层二次认证。不要把"加了 noindex"误当成"管理端已受保护"。

**SPA 的一个实操注意点**：管理端首屏会有一小段白屏（等待 JS 加载与接口返回）。可用 Nuxt 的 SPA loading template 提供占位，但**这不是必须的**，先按普通后台页做即可（符合 C4：不做视觉打磨）。

## 7. 对象存储与 CDN（Cloudflare R2）

### 7.1 上传内容

**仅上传派生图（thumbnail / preview），不上传原图。** 原图留在 NAS，保留隐私且避免大额存储开销。

### 7.2 R2 配置要点

**代码只依赖四个通用配置，与「哪家 S3 服务」无关：**

| 项目     | 值 / 说明                                                                                                       |
| -------- | --------------------------------------------------------------------------------------------------------------- |
| 协议     | S3 兼容（R2 官方支持）                                                                                          |
| Endpoint | `https://<account-id>.r2.cloudflarestorage.com`                                                                 |
| Region   | `auto`                                                                                                          |
| 凭据     | R2 API Token（Object Read & Write），非 Cloudflare 全局 API Key                                                 |
| 公开基址 | `FRAMEFOLIO_S3_PUBLIC_BASE_URL`，**任意字符串前缀**；填 `r2.dev`、自定义域名或 MinIO 地址均可，代码行为完全相同 |

**部署建议（非代码约束）：使用自定义域名而非 `r2.dev`**

- R2 提供 S3 兼容的**上传/写入 API**（代码用的就是它），这与「图片如何被公开读取」是**两件独立的事**
- 图片的公开读取需要一个公开地址，有两种选择：

  | 选择                   | 特点                                                                         |
  | ---------------------- | ---------------------------------------------------------------------------- |
  | `r2.dev` 子域          | 开箱即用，但 Cloudflare 定位为**非生产用途**，有**速率限制**且不走缓存体系   |
  | **自定义域名**（推荐） | 需把域名接入 Cloudflare；可获得 **CDN 缓存**，且 R2 → 互联网**出网流量免费** |

- 这是**运维层面的性能/成本选择**，不影响开发：配置里改一个字符串即可切换
- 由于我们的文件名含 revision（内容寻址），可直接设置长期 `immutable` 缓存，**更新图片时 URL 自动变化，无需手动刷新 CDN**

> 请以 Cloudflare 官方文档为准：[Expose R2 bucket contents to the Internet](https://developers.cloudflare.com/r2/buckets/public-buckets/) 与 [R2 Limits](https://developers.cloudflare.com/r2/platform/limits/)。

### 7.3 对象键

与本地文件名完全一致（含 `FRAMEFOLIO_S3_PREFIX` 前缀）：

```text
<prefix>/<id>-<revision>-thumbnail.webp
<prefix>/<id>-<revision>-preview.webp
```

### 7.4 切换安全性

不做「全局盲切」，而是**逐张判定**：

- `remote.revision === source.revision` → 返回 R2 URL
- 否则 → 回退本地 `/media/`

这样即使只上传了一部分，站点也不会出现白图，且新同步的照片会自然补齐。管理端提供完整性统计（已上传 / 待上传）与一键补传。

### 7.5 一致性与清理

- **删除**：先删本地（软删除），再删对象；对象删除失败记录为待清理项，由后续同步幂等重试
- **孤儿对象**：同步清理阶段可选用 `ListObjects` 比对索引，删除不再被引用的对象（默认关闭，需显式开启，避免误删同桶其他数据）。R2 的 `ListObjects` 无额外费用，但**默认仍不开启**以防误删
- **可测试性**：S3 兼容协议让我们可用 MinIO 容器在本地完整验证上传 / 切换 / 回退链路，**无需真实 R2 凭据**
- **CORS**：`/media` 本地源与 R2 域名是两个不同源。若前端仅用 `<img src>` 展示则不受同源策略限制，无需 CORS 配置；但若将来需要 canvas 导出或 `fetch` 图片数据，则需在 R2 桶上配置 CORS

### 7.6 实测发现的并发缺陷（重构必须修复）

**已通过真实执行复现**（定向并发测试 3/3 命中）：

`scripts/lib/gallery-sync.ts` 存在两处**共享临时路径**，在两个同步进程同时运行时互相破坏：

| 位置                      | 问题                                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------------- |
| `gallery-sync.ts:467`     | 索引临时文件固定为 `photos.json.tmp`，两个进程**写同一文件**                                      |
| `gallery-sync.ts:536-539` | `cleanTemporaryFiles` 启动时**删除 `generated/` 下所有 `.tmp`**，会删掉另一个进程正在写的临时文件 |

复现结果：进程 A 报 `ENOENT: rename ... .tmp`，`failed 1`、退出码 1，且 `generated/` 最终只有 48 个文件（应为 50）——**有 1 张照片的派生图缺失**。

**当前为何没暴露**：CLI 是人工执行，天然串行；随机并发压测 8/8 通过（窗口很窄）。但 Web 管理端引入「网页按钮」后，**「点按钮」与「敲 CLI」同时发生的概率显著上升**，且管理端还可能并发派发（如快速连点、多标签页），必须修复。

**修复方案**（阶段 2 一并完成）：

1. 临时文件名加入 `process.pid` 与随机串（`photos.json` 同样处理），消除跨进程冲突
2. `cleanTemporaryFiles` 只清理**属于已死进程**的残留（如按 `mtime` 超过阈值判定），而非无差别删除所有 `.tmp`
3. 全局唯一锁（`data/.state/sync.lock`）从源头保证同一时刻仅一个同步任务——这是主要防线，1 与 2 是纵深防御

> 这说明「加同步锁」不只是为了省资源，而是**修复一个已存在的正确性缺陷**。

## 9. 性能评估

### 9.0 实测数据（本机 Apple M4 / 10 核，25 张真实照片）

为避免空谈，以下为**真实执行测量**，样本为仓库内 25 张照片（共 482 MP，最大单张 42.2 MP）：

| 场景                  | 耗时       | 峰值内存       | CPU 占用    |
| --------------------- | ---------- | -------------- | ----------- |
| 首次全量同步（25 张） | **7.6 s**  | **289–340 MB** | **1.00 核** |
| 增量同步（无变化）    | **0.08 s** | 87 MB          | ~0          |
| 最大单张（42.2 MP）   | **0.48 s** | 172 MB         | 1 核        |

**关键结论一：同步不阻塞 HTTP 服务（已实测）。**

启动真实 Nuxt 服务，在**强制全量重生成**的同时持续请求接口：

| 路由                          | 同步期间延迟                |
| ----------------------------- | --------------------------- |
| `/api/photos`（1188 次采样）  | 中位 **0.6 ms**，p95 0.8 ms |
| `/media/:file`（1176 次采样） | 中位 **0.6 ms**，p95 0.9 ms |

对比空闲基线（中位 1.1 ms），**延迟无劣化**。原因：同步在**子进程**中运行，sharp 的原生处理在 libuv 线程池，与主进程的事件循环互不争抢。

**关键结论二：只占 1 个 CPU 核心。** 管线是顺序 `for` 循环（`gallery-sync.ts:194`），同一时刻只处理一张，因此不会吃满多核——**对低配 NAS 友好**。

**关键结论三：内存峰值约 300–340 MB**，主要来自最大单张的像素缓冲（`宽 × 高 × 4` 字节，42 MP ≈ 170 MB）。这是**最需要关注的指标**。

### 9.0.1 NAS 上的预期换算（重要）

上述数据来自 **M4 / 10 核**，不能直接套用到 NAS。NAS 通常为低功耗 x86（Celeron / N 系列）或 ARM，单核性能约为 M4 的 **1/4 ~ 1/8**。粗略预期：

| 场景                | M4 实测 | NAS 预估（按 1/5 计）                         |
| ------------------- | ------- | --------------------------------------------- |
| 首次全量 100 张     | ~30 s   | **2.5 ~ 5 min**                               |
| 新增 1 张（增量）   | ~0.3 s  | 1.5 ~ 3 s                                     |
| 增量扫描（仅 stat） | 0.08 s  | **< 1 s**                                     |
| 内存峰值            | 340 MB  | **相近（主要取决于图像分辨率，与 CPU 无关）** |

**结论：会卡吗？**

- **网页浏览**：不会。已实测同步期间接口延迟无劣化
- **NAS 其他服务**：影响很小。同步只占 1 核，且不是持续负载——只有检测到变更时才处理
- **唯一体感明显的场景**：首次导入数百张（可能持续数分钟），此时 NAS 会有一个核心持续忙碌
- **内存是关键**：若 NAS 可用内存 < 768 MB，处理 40 MP 以上的大图可能出现 OOM，需下调并发或限制单张最大像素

### 9.1 镜像与依赖

**镜像体积不增加。** runtime 镜像已包含 sharp 与 tsx——`Dockerfile:34` 显式验证 `import('sharp')`，因为 `sync` 服务复用同一镜像。新增的 S3 SDK 仅为服务端依赖，且可外部化，不进入客户端产物。

### 9.2 请求延迟

**不被同步阻塞（已实测，见 §9.0）。** sharp 的原生处理运行在子进程的 libuv 线程池而非主线程，后台同步期间 HTTP 仍可正常响应。需限制并发（默认 1）以保护 NAS。

### 9.3 资源开销

| 项目       | 评估                                                                                      |
| ---------- | ----------------------------------------------------------------------------------------- |
| 待同步检测 | 每次 `stat` 比对；1000 张本地文件为毫秒级（实测 64 ms），仅在打开管理端时执行，无常驻开销 |
| 图片处理   | 实测 42 MP 单张 0.48 s（M4）；NAS 预估 1.5–3 s/张，且仅处理变更项                         |
| 内存       | 峰值 ≈ 最大单张 `宽 × 高 × 4` 字节；实测 42 MP → 约 300–340 MB 总峰值                     |
| 上传       | 内存恒定（流式落盘），不受文件大小影响                                                    |
| 后台常驻   | **无**。没有定时器、没有轮询进程；不点同步按钮就零开销                                    |

### 9.4 实际收益

R2 + CDN 直接降低图片加载延迟，并**减少 NAS 出网带宽与磁盘读取压力**，这正是引入它的目的；R2 不计出网流量费，成本主要取决于存储量与操作次数。

### 9.5 主要性能风险

**NAS 算力与内存。** 首次全量导入（数百张）会长时间占用一个 CPU 核心，这是主要体感来源。与现状（CLI 全量同步）相同，但若在管理端点击「全部重新生成」需给出明确提示与进度反馈，避免误以为卡死。针对低配 NAS 的可调项：

- `FRAMEFOLIO_SYNC_CONCURRENCY`（默认 1，NAS 建议保持 1–2）
- 限制单张最大像素，超出则跳过并报警，避免内存峰值失控
- 文档提示 `UV_THREADPOOL_SIZE` 的调优方式

## 12. 已确认的决策

原「待确认项」已全部有结论：

| #   | 问题                   | 决定                                       | 影响                                                                                                                   |
| --- | ---------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| 1   | 对象存储服务商         | **Cloudflare R2**（S3 兼容协议）           | 用 `@aws-sdk/client-s3`，不引入 `ali-oss`；保留兼容阿里云 OSS / MinIO 的能力                                           |
| 2   | 是否绑定 CDN 域名      | **是，必须自定义域名**（不用 `r2.dev`）    | 这是**部署时的运维选择，不是开发前置条件**（见下）                                                                     |
| 3   | 软删除保留期           | **软删除，不自动清理**                     | 实现只需 `move` 而非 `rm`，成本低；不写清理任务 = 更少代码、无自动删除风险。`.trash/` 不在 `originals/` 内，不影响扫描 |
| 4   | 是否做定时轮询自动同步 | **不做**（已确认砍掉）                     | 触发入口只保留「立即同步」按钮与 CLI 两个显式动作；省去轮询特有逻辑（§5）                                              |
| 5   | 单容器 vs 双容器       | **单容器**（gallery 改为可写），反代层加固 | 只改一行 compose；两个方案共用同一份代码，A → B 随时可切（见 §4.1.1）                                                  |

### 12.1 关于「自定义域名」的定位（澄清）

**代码开发完全不需要域名。** 实现是通用的 S3 客户端，只认「endpoint + 凭据 + 桶名 + 公开基址」四个配置：

```env
FRAMEFOLIO_S3_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com
FRAMEFOLIO_S3_PUBLIC_BASE_URL=https://img.example.com   # ← 这里填什么，代码不关心
```

`FRAMEFOLIO_S3_PUBLIC_BASE_URL` 只是一个**字符串拼接前缀**。填 `r2.dev`、填自定义域名、填 MinIO 的 `http://localhost:9000`——**代码行为完全相同**，没有任何分支。

因此：

- **开发阶段**：用 MinIO 在本地跑，无需 R2、无需域名、无需真实凭据
- **部署阶段**：你按需填公网地址即可，随时可改，改完重启生效
- 「必须用自定义域名」是**给你的运维建议**（因为 `r2.dev` 有速率限制且不走缓存），**不是代码约束**

> 结论：这一点不阻塞任何开发工作，无需提前确认。

### 12.2 关于 CDN 域名的**跨域**问题（唯一与代码相关的点）

有一个与代码有关、但同样**不阻塞开发**的点：本地源是 `/media/...`（你的站点域名），R2 源是另一个域名，两者是**不同源**。

- 目前前端只用 `<img src>` 展示图片 → **不受同源策略限制，无需任何 CORS 配置**
- 只有当将来需要 `fetch()` 图片数据或 `canvas` 导出时才需要配 CORS

所以现在**什么都不用做**。按现有功能（纯展示）不会遇到跨域问题。

### 12.3 同步触发方式（已确认）

**同步只有两个触发入口，都是显式动作：**

1. **管理端「立即同步」按钮** —— 日常使用。SMB 拷完照片、手机上传完、删除完，点一下即可
2. **命令行 CLI**（`pnpm gallery:sync` / `docker compose run --rm sync`）—— 批量导入、故障恢复、脚本化、排查问题时使用

**明确不做**：

- 定时轮询自动同步（原 `FRAMEFOLIO_SYNC_INTERVAL` 设计已取消）
- 上传后自动触发同步
- 删除后自动触发同步

**因此不存在任何「同步设置」**：没有间隔、没有开关、没有去抖参数。行为完全由你的点击决定，按钮按下之前网站状态不会改变。

两者共用同一把锁 `data/.state/sync.lock`（§5.4）；并发缺陷的修复见 §7.6。
